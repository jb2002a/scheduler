# 베이스라인 실험: 기본 모델만으로 시간표를 짤 수 있는가

## 1. 목적

도구나 솔버, 에이전트 구조 없이 **강의 데이터 전체를 프롬프트에 넣고 기본 모델에게 시간표를 요청**했을 때 다음 두 가지를 확인한다.

1. 할루시네이션 없이 실제 데이터에 있는 과목만으로 시간표를 만드는가
2. 시간 충돌, 학점, 사용자 조건을 정확히 지키는가

이 결과로 에이전트 구조(`DESIGN.md`)가 실제로 필요한지, 필요하다면 어느 부분에서 필요한지 판단한다.

- 베이스라인이 충분히 정확하다 → 에이전트 구조를 단순화한다.
- 특정 유형의 오류가 반복된다 → 그 오류를 막는 쪽으로 도구와 솔버를 설계한다.

## 2. 실험 조건

### 2.1 모델 호출

- 도구 호출(function calling) 없음
- 시스템 프롬프트에 강의 데이터 전체를 CSV 텍스트로 넣음
- 프롬프트는 최소한으로 작성한다. 채점을 위해 출력 형식(JSON)만 지정한다.

```
너는 원광대학교 시간표를 짜주는 도우미야.
아래 강의 목록에 있는 과목만 사용해서 사용자 요청에 맞는 시간표를 만들어.
시간 표기는 요일 뒤에 교시가 붙는 형식이야. (예: 목3금12 = 목 3교시, 금 1·2교시)

[강의 목록]
과목구분,과목명,학점,시간
전공선택,자료구조,3,목3금12
...

응답은 아래 JSON 형식으로만 해.
{
  "feasible": true,
  "courses": [{ "name": "...", "credits": 3, "time": "목3금12" }],
  "total_credits": 18,
  "explanation": "..."
}
요청을 만족하는 시간표가 없으면 "feasible": false 로 답하고 이유를 explanation에 적어.
```

### 2.2 변수

| 변수 | 값 |
|---|---|
| 데이터 크기 | 100개(실제 데이터), 300개, 500개 |
| 모델 | 소형 모델 1개, 상위 모델 1개 (확정 필요) |
| 반복 횟수 | 시나리오마다 5회 (응답 편차 측정) |

300개, 500개 데이터는 실제 데이터를 기반으로 과목명과 시간을 변형해 생성한다. 실제 데이터만 쓸 때보다 현실성은 떨어지지만, 데이터가 늘어날수록 할루시네이션이 늘어나는지 보기 위해 필요하다.

## 3. 테스트 시나리오

쉬운 요청에서 어려운 요청 순으로 구성한다.

| ID | 유형 | 요청 예시 |
|---|---|---|
| S1 | 단일 조건 | 18학점으로 짜줘 |
| S2 | 요일 | 18학점, 수요일 공강 |
| S3 | 교시 | 18학점, 아침 1교시 비워줘 |
| S4 | 교시 | 18학점, 점심(4교시) 비워줘 |
| S5 | 복합 | 18학점, 수요일 공강, 점심 비우기, 주 3일 |
| S6 | 과목 지정 | 자료구조는 꼭 넣고 영어회화는 빼줘 |
| S7 | 구분별 학점 | 전공 12학점 이상, 총 18학점 |
| S8 | 불가능한 요청 | 해가 없도록 일부러 만든 조건 조합 |
| S9 | 멀티턴 | S2 결과에 "아침도 비워줘"를 이어서 요청 |
| S10 | 멀티턴 | S9 결과에 "아까 수요일 공강은 취소해줘" |

S8은 모델이 불가능하다고 인정하는지, 아니면 조건을 몰래 어긴 시간표를 내놓는지 확인하는 용도다.
불가능 여부는 실험 전에 직접 계산해서 정답을 확정해 둔다.

## 4. 채점 (코드로 자동 검증)

LLM이 아닌 **결정적인 검증 코드**로 채점한다. 이 검증기와 시간 파서는 나중에 에이전트와 솔버 테스트에도 그대로 재사용한다.

### 4.1 오류 유형

| 코드 | 오류 | 판정 방법 |
|---|---|---|
| E1 | 존재하지 않는 과목 | 과목명이 데이터에 없음 |
| E2 | 속성 오기재 | 과목은 있지만 학점이나 시간이 데이터와 다름 |
| E3 | 시간 충돌 | 같은 요일, 같은 교시에 두 과목 이상 |
| E4 | 과목 중복 | 같은 과목이 두 번 이상 들어감 |
| E5 | 조건 위반 | 사용자 요청(공강, 교시, 학점 범위 등)을 어김 |
| E6 | 학점 계산 오류 | 모델이 적은 `total_credits`와 실제 합계가 다름 |
| E7 | 실행 가능성 오판 | 불가능한 요청에 시간표를 내놓음, 또는 가능한데 불가능하다고 답함 |
| E8 | 형식 오류 | JSON 파싱 실패 |

E1과 E2는 할루시네이션, E3부터 E7까지는 추론 오류로 분류한다.

### 4.2 지표

- **완전 정답률**: 오류가 하나도 없는 응답의 비율
- **오류 유형별 발생률**: E1~E8 각각
- **데이터 크기별 추이**: 100 → 300 → 500에서 할루시네이션이 늘어나는지
- **응답 일관성**: 같은 시나리오 5회 반복 시 결과 편차

### 4.3 결과 표 (예시 양식)

| 모델 | 데이터 | 완전 정답률 | E1 | E2 | E3 | E5 | E6 | E7 |
|---|---|---|---|---|---|---|---|---|
| 소형 | 100 | | | | | | | |
| 소형 | 300 | | | | | | | |
| 상위 | 100 | | | | | | | |

## 5. 결과 해석 기준

| 결과 | 판단 |
|---|---|
| 완전 정답률이 높고 데이터가 늘어도 유지됨 | 에이전트 구조를 최소화. 검증기만 붙여 재시도하는 방식도 검토 |
| E1, E2(할루시네이션)가 많음 | `search_courses`로 데이터를 조회하게 하고, 과목 ID 기반으로 다루게 함 |
| E3, E5(충돌, 조건 위반)가 많음 | 시간표 조합을 솔버로 넘기는 구조가 필요함 |
| E6(학점 계산)이 많음 | 계산을 코드로 처리 |
| E7(불가능 판단)이 틀림 | 솔버의 infeasible 판정과 충돌 원인 반환이 필요함 |
| 멀티턴(S9, S10)에서만 실패 | 조건 목록을 세션 상태로 관리하는 구조가 필요함 |

정확도와 함께 비용도 확인할 것.

## 6. 구현 범위

```
scheduler/
├── data/
│   └── courses.csv            # 실제 데이터 100개
├── db/
│   └── time_parser.py         # "목3금12" → [(THU,3), (FRI,1), (FRI,2)]
├── experiments/
│   └── baseline/
│       ├── generate_data.py   # 300개, 500개 데이터 생성
│       ├── scenarios.json     # 시나리오와 각 조건, S8 정답
│       ├── run.py             # 모델 호출, 응답 저장
│       ├── validator.py       # E1~E8 자동 채점
│       └── results/           # 원본 응답과 채점 결과
```
