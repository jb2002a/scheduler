# 마일스톤과 우선순위

`DESIGN.md`의 10장(개발 순서)을 기준으로, 의존 관계와 위험도를 반영해 우선순위를 다시 정리했다.
`DESIGN.md`는 설계의 기준 문서로 그대로 두고, 이 문서는 **무엇을 어떤 순서로 만들지**만 다룬다.

## 1. 우선순위 원칙

1. **정확성의 바닥부터 만든다.** 파서, 데이터, 검증기가 틀리면 그 위의 솔버, 에이전트, UI가 모두 틀린다.
2. **여러 곳에서 재사용되는 것을 먼저 만든다.** 시간 파서와 검증기는 베이스라인 실험, 솔버 테스트, 에이전트 확인에 모두 쓰인다.
3. **불확실한 가정은 일찍 검증한다.** 실제 데이터가 설계 가정과 다르면 뒤로 갈수록 수정 비용이 커진다.
4. **대화 구현 전에 솔버 위임을 측정한다.** 세션, 되묻기, UI를 만들기 전에, 같은 시나리오에서 솔버 도구가 순수 LLM보다 나은지 확인한다.
5. **UI는 마지막에 붙인다.** 에이전트가 CLI에서 정확히 동작한 다음에 화면을 얹는다.

## 5. 우선순위 요약

| 순위 | 마일스톤 | 상태 | 이유 | 대략적 비중 |
|---|---|---|---|---|
| P0 | M0 데이터 기반 | 완료 | 모든 단계의 선행 조건, 설계와 데이터의 차이 해소 | 작음 |
| P0 | M2 솔버 단독 | 완료 | 정확성 보장의 핵심. 조건 JSON을 CP-SAT으로 푼다 | 큼 |
| P0 | M1 베이스라인 | 완료 | `gpt-5.6-luna` 150회. 띄어쓰기는 오류에서 제외. 300과목 완전 정답 80%, 실패는 E3·E5 | 작음~중간 |
| P1 | M3 솔버 도구 비교 | 완료 | 같은 S1–S10에서 `schedule`→솔버 시간표를 채점. 100·300·500 모두 50/50 | 작음~중간 |
| P1 | M4 에이전트 연결 | 완료 | 세션 + `schedule`/`search_courses`/`ask_user` CLI. S1–S10·되묻기·아침 기본해석 12/12 | 큼 |
| P2 | M5 UI | 완료 | Streamlit 채팅+주간 그리드. `streamlit run app/main.py` | 중간 |

권장 진행 순서: **M0 → (M1 ∥ M2) → M3 → M4 → M5**. M0–M5는 끝났고, 마일스톤은 여기까지다. 졸업요건 반영만 보류다. 솔버 시간표가 베이스라인보다 낫다는 비교는 M3에서 끝났으므로 별도 평가 마일스톤은 두지 않는다.

M3는 `DESIGN.md` 10장에 없는 확인 단계다. 대화 구현보다 앞에 둔다.

- 문장, 모델, 반복, 데이터 크기는 M1과 같다. S1–S10, `gpt-5.6-luna`, 5회, 100·300·500과목.
- 모델은 과목을 고르지 않는다. 요청을 조건 JSON으로 바꿔 솔버를 호출한다.
- 채점 대상은 솔버가 반환한 시간표다. 채점기는 M1의 E1–E8을 그대로 쓴다.
- 비교 기준은 M1 완전 정답률이다. 100과목 88%, 300과목 80%, 500과목 48%.
- S9·S10은 이전 발화를 메시지로만 잇는다. 매 턴 현재 조건 전체를 다시 내고, 세션 저장소는 만들지 않는다.
- 과목 지정은 이름으로 받는다. 코드가 하나의 `course_id`로 바꾼 뒤 솔버에 넣는다. 이름이 둘 이상이면 그 호출은 실패로 기록한다.
- `ask_user`, `search_courses`, UI는 만들지 않는다.

M4는 서버 세션에 조건을 쌓고, 모델은 `add`/`remove`만 보낸다. 카탈로그는 프롬프트에 넣지 않고 `search_courses`로 찾는다.

- 도구: `search_courses`, `schedule(add/remove/n)`, `ask_user`. `course`는 `course_id`만 받는다.
- CLI는 `python -m agent.cli`. 확인은 `python -m agent.check_scenarios`로 S1–S10 1회와 되묻기·아침 기본해석을 돌린다.
- 같은 이름 두 과목은 `ask_user`로 끝내고 조건은 바꾸지 않는다. 아침은 `free_slots` `[0, 1]`이고 되묻지 않는다.
- UI는 M5에서 붙인다.
